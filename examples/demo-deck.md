[ПРОТОТИП · Фикс]
## Фикс: ACK только после сохранённого результата

```py
async def on_update(update: Update) -> None:
    # 1. task_id создаём синхронно, до любой работы
    task_id = await store.register(update.update_id)
    try:
        result = await handle(task_id, update)
        await store.save_result(task_id, result)
        await bot.reply(update, result)
    except Exception:
        await store.rollback_offset(update.update_id)
        raise
    if await store.task_id_for(update.update_id) == task_id:
        await store.ack(update.update_id)
```

### task_id сразу {green}
у каждого update есть запись в БД до работы
### Откат offset {green}
при ошибке update вернётся снова
### Сверка перед ACK {green}
подтверждаем свой task_id, а не чужой

!!orange Повторная доставка теперь возможна. Значит, нужна идемпотентность

## Главная мысль

> LLM-агент — ненадёжный компонент. Надёжность даёт инженерия вокруг него.

- контракт задачи, состояние в БД, идемпотентность
- права вне текста и сквозные тесты

[ТЗ · Координация]
## Сроки и повторы контролирует код, а не модель

### LLM {blue}
- понимает запрос
- пишет сводку по готовым ответам
### КОД {green}
- считает ответы и сроки
- делает повторы
- правило завершения `ALL_OR_DEADLINE`
- пишет состояние в БД

[ИТОГ · Что унести]
## Три вывода для Python-разработчика

1. **Контракт до отправки**: цель, формат, сроки и лимиты задаёт код
2. **Состояние в БД**, а не в памяти процесса: рестарт не должен терять задачи
3. **Идемпотентность** каждого эффекта: повторная доставка — норма, а не баг
   - проверяется сквозным тестом с падением в любой точке
